# Contributing to get-enlace.github.io

## Layout

- `src/pages/index.tsx` — the landing page.
- `docs/` — everything under `/docs`, organized by task rather than by
  repo or internal concept (see [`start-here/`, `guides/`, `adapters/`,
  `reference/`, `community/`). Sidebar order comes from each file's
  `sidebar_position` frontmatter, or a folder's `_category_.json`
  (autogenerated from folder structure — see `sidebars.ts`).
- `static/img/` — brand assets, copied from the org's
  [`.github`](https://github.com/get-enlace/.github) repo.

### What goes where

- **`start-here/`** — the path a first-time reader follows: what Enlace
  is, installing it, a guided demo.
- **`guides/`** ("Building a Chain") — task-oriented how-tos for actually
  using the canvas: connecting/mapping, Raw JSON bodies, credentials,
  running a chain. Write these as "how do I…", not "here's how it's
  built".
- **`adapters/`** — per-framework install/usage, one page each.
- **`reference/`** — terse, factual lookup material (credential types,
  release channels) — no narrative, no "why".
- **`community/`** — feature requests and a pointer to each repo's own
  `ARCHITECTURE.md`/`CONTRIBUTING.md` for internals. Deliberately *don't*
  reproduce architecture/data-model content here — this site is for
  people using Enlace, not hacking on it; that lives with the code.

If a page mostly restates a README or explains an internal type/algorithm
by name, it's probably in the wrong place — turn it into a task ("how do
I…") or cut it and link to the source repo instead.

## Local development

```bash
npm install
npm start
```

Opens `http://localhost:3000` with hot reload.

```bash
npm run build   # static build into build/ — fails on a broken internal link
npm run serve   # serve that build locally
npm run typecheck
```

## Keeping docs accurate

This site documents behavior owned by other repos
(`enlace-ui`, `enlace-js`, `enlace-dotnet`, `enlace-examples`). When one of
those repos changes something documented here — a new adapter, a new
credential type, a data-model change — update the corresponding page in
this repo too. There's no automated sync; it's a manual step as part of
that change.

## CI/CD

`.github/workflows/deploy.yml` — on every push to `main`: `npm ci && npm
run build`, then deploy `build/` to GitHub Pages via
`actions/upload-pages-artifact` + `actions/deploy-pages`. No dev/prod
split like the package repos — a docs site has no registry or version to
gate, just build-and-publish on merge. Requires the repo's Settings →
Pages → Source set to "GitHub Actions".
